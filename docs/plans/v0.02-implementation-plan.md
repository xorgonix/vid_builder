# vid-build 0.02 — Implementation Strategy and Plan

**Source:** `SPECS/newvid-build 0.02 — Creative Direction, Storyboard and Animatic Change Specification.md`
**Base commit:** `40accfe` (v0.01 vertical slice, all phases of the v3.1 spec implemented)
**Target:** Concept → Brief → Structure → Scenes → Beats → Shots → Blocking → Animatic → Production → Review → Edit → Export

---

## 1. Ground rules

1. **Evolution, not rewrite.** Every item in spec §2 is preserved. No module is replaced wholesale.
2. **SQLite stays the sole source of truth.** New state is tables, not files.
3. **Human authority is untouched.** New AI surfaces propose and are selectively applied.
4. **Forward-only, transactional, tested migrations.** Never migrate the live database without a verified copy.
5. **No phase is "done" until its tests pass and the existing vertical slice still works end to end.**
6. **Commit after every sub-step.** Each commit must build, vet and test green.
7. **Fewest mistakes = smallest steps.** Prefer many small commits over few large ones.

---

## 2. Strategy

### 2.1 Vertical slices, not horizontal layers

Each phase is delivered as a working vertical slice:

```
migration → repository → domain/service → route → template/fragment → test → commit
```

We never land "all the SQL" or "all the handlers" separately. A creator can use the
feature the moment the phase merges.

### 2.2 Phase gates

Every phase ends with a **gate**:

| Gate | Requirement |
|---|---|
| Build | `templ generate && go build ./...` clean |
| Static | `go vet ./...` clean |
| Unit | `go test ./...` green, including new tests |
| Migration | Applies to a **copy** of a representative v0.01 database, and to an empty database |
| Regression | The v0.01 end-to-end path (project → brief → outline → blocking → generate → review → export) still works |
| Docs | Claims in docs match behaviour (no overclaiming) |

### 2.3 Migration safety protocol

Applied to Phase 1 (first schema change) and repeated for every later migration:

1. Copy the live `data/vidbuild.db` to `data/backups/pre-v0.02-<ts>.db` (plus a manifest).
2. Add a numbered migration; run it against the **copy** first.
3. Verify: counts preserved, implicit beats created, `foreign_key_check` clean,
   `integrity_check = ok`.
4. Back up again, then run against the live database.
5. Document the rollback note (restore from the pre-v0.02 copy).

### 2.4 Migration framework change (Phase 0 prerequisite)

The v0.01 `db.migrate()` applies `schema.sql` plus ad-hoc `ALTER TABLE` statements. v0.02
needs **ordered, recorded** migrations:

- New table `schema_migrations (version INTEGER PRIMARY KEY, name TEXT, checksum TEXT, applied_at TEXT)`.
- `internal/db/migrations/NNNN_name.sql`, embedded and applied in order inside a transaction.
- Existing v0.01 databases are detected and backfilled with migration `0001` (the v0.01 schema).
- Each migration is recorded with a checksum; a changed checksum on an applied migration
  is a startup error (protects against silent divergence).

### 2.5 Compatibility strategy

- **Implicit beats.** A scene always has at least one beat; simple projects hide the layer.
- **Blocking v2 reader.** Existing v1 blocking JSON is parsed by a compatibility reader and
  upgraded **in memory**; a new version is only persisted on the next human save. Existing
  rows are never rewritten.
- **Prompt layers.** `mode: "lock"` rows from v0.01 migrate to `locked: true` with
  `mode: "append"` (or their prior textual mode) on read; the enum loses `lock` as a text mode.
- **shot_links.** Existing `metadata_json` rows stay; validated structured handoff is added
  alongside and preferred when present.

### 2.6 Security-first sequencing

Spec §13 makes authorization a **release blocker**. So Phase 0 closes it *before* adding new
mutation routes, otherwise every new route would inherit the same gap.

### 2.7 Test harness first

Phase 0 also lands the shared test harness so every later phase writes tests cheaply:

- `internal/db` test helper: fresh temp SQLite, migrate, return `*store.Store`.
- `internal/web` test helper: build the `http.Handler`, a cookie-jar session, login helper,
  CSRF token extractor, and a table-driven authorization matrix runner.
- `internal/planner` fixture loader: deterministic JSON responses (no live LM Studio).
- `internal/workflows` fixture workflow for generation without ComfyUI network calls
  (uses a stub adapter / fixture graph), so CI never depends on external services.

## 4. Phase plan

### Phase 0 — Stabilize the base

**Goal:** make the foundation safe to build on.

| Step | Deliverable | Files |
|---|---|---|
| 0.1 | Numbered migration framework + `schema_migrations` | `internal/db/migrations/*`, `internal/db/db.go` |
| 0.2 | Test harness (db, web session/CSRF, planner fixtures, workflow fixture) | `internal/**/testutil_test.go` |
| 0.3 | Authorization audit and repair for **every existing mutation route** | `internal/web/server.go`, `middleware.go`, `handlers_*.go` |
| 0.4 | Prompt lock semantics: remove `ModeLock`, add `Locked bool`, `Positive`, `Negative`, `Priority` | `internal/prompt/prompt.go`, prompt workbench |
| 0.5 | Structured validation: blocking coordinate/NaN bounds, transition docs, planner JSON, cross-project IDs | `internal/blocking`, `internal/web`, `internal/planner` |
| 0.6 | Spec cleanup: remove conversation fragments/typos from the v3.1 spec; fix overclaims | `SPECS/mark2-v3.1-specification.md`, `docs/*` |

**Tests:** authorization matrix for all existing routes (owner/editor/reviewer/viewer/
non-member/unauthenticated); migration applies to empty + copied v0.01 DB; prompt compile
with locked layers; malformed planner JSON rejected and retained as failed proposal evidence.

**Exit:** all existing tests pass; authorization matrix passes for current routes; docs no
longer overclaim. **Commits:** one per step (0.1 … 0.6).

### Phase 1 — Beats and narrative development

**Goal:** insert the dramatic beat layer without breaking simple projects.

| Step | Deliverable |
|---|---|
| 1.1 | Migration: `beats` table; `shots.beat_id`; one implicit beat per existing scene; backfill; `beat_id` required |
| 1.2 | Store/service: beat CRUD, ordering/move, validation, revision; `scene → beats → shots` derivation |
| 1.3 | Routes: `POST /scenes/{sceneID}/beats`, `PATCH/DELETE /beats/{beatID}`, `POST /beats/{beatID}/move`, `POST /beats/{beatID}/propose-shots` |
| 1.4 | Templates: outline hierarchy Section → Scene → Beat → Shot; implicit containers hidden until requested |
| 1.5 | Planner split: **structure proposal** (sections+scenes only), **beat proposal** (one scene), **shot-breakdown proposal** (one beat) with justification + suggested production method |
| 1.6 | Proposal UX: apply all / apply selected / edit before apply / reject with reason / regenerate from feedback / diff vs current |
| 1.7 | Invalidation: scene purpose/brief stales dependent beat & shot proposals (mark stale, never delete) |

**Exit:** a creator expands one concept through scenes and beats into justified shots
without editing JSON.

### Phase 5 — Prompt and endpoint integration

| Step | Deliverable |
|---|---|
| 5.1 | Compiler emits separate first/last/motion positive+negative, reference/identity guidance, workflow auxiliary fields |
| 5.2 | **Lossy merge report** for single-prompt workflows — never pretend fields stay independent |
| 5.3 | Wan-oriented ordering: subject/setting → initial state → action → end state → secondary motion → shot/camera → lighting/colour → style/mood → continuity |
| 5.4 | End prompt derived from the accepted **end state**, not a rewrite of the start prompt |
| 5.5 | Linting: near-identical endpoints, no visible change, contradictory camera, conflicting lighting, too many primary actions, invariant changed without authorization, over-budget, dropped structured fact |
| 5.6 | Endpoint precedence on cards: selected final → concept → blocking SVG → empty prompt |
| 5.7 | Continuity state feeds prompt layers |

**Exit:** approved narrative/blocking compiles into separate, inspectable start/end/motion
prompts with no near-clone endpoints.

## 5. Test strategy

| Layer | Content |
|---|---|
| **Unit** | beat validation/ordering; blocking v2 parse/validate/compare/interpolate; continuity merge rules; stable-ID matching; prompt compilation + lock semantics; linting; transition validation; metric bounds; animatic timing; cue overlap warnings |
| **Store** | v0.01→v0.02 migration with real scenes/shots; implicit beat creation; optimistic conflicts; version supersession; cross-project ID rejection; cascades; stale propagation; shot link CRUD; backup includes new tables |
| **Authorization matrix** | every mutation family × owner/editor/reviewer/viewer/non-member/unauthenticated, over direct HTTP (not just hidden buttons) |
| **Planner contracts** | fixture-driven: valid accepted; malformed rejected+recorded; partial application; approved data untouched; context budget respected; shot has change+justification; continuity distinguishes inherited vs recomposed |
| **Web integration** | concept→brief→scene→beat→shot; blocking save/reload; touch vs property payload equivalence; animatic reflects current revisions; duration totals; endpoint precedence; offline conflict; production blocked without approved inputs |
| **End-to-end** | the §16.6 acceptance scenario automated against fixture workflows (no live ComfyUI required), plus a manual run against real ComfyUI/LM Studio |

## 6. Risk register

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Migration corrupts existing projects | Med | High | Copy-first protocol (2.3), implicit-beat backfill, integrity + FK checks, pre-migration backup, recorded checksums |
| Beat layer over-complicates simple projects | Med | Med | Implicit beats hidden in UI; progressive disclosure |
| Blocking v2 breaks existing blockings | Med | High | Compatibility reader; never rewrite v0.01 rows; tests over real payloads |
| Authorization missed on a new route | Med | High | Phase 0 matrix harness; new route template requires the matrix be extended (enforced by a test that enumerates routes) |
| Prompt compiler fakes independence | Med | High | Explicit lossy merge report + lint; tests assert the report appears |
| Animatic leaks credentials/paths | Low | High | `/animatic/data` returns a bounded document; contract test asserts absence of secrets/paths |
| Scope creep across 8 phases | High | Med | Phase gates, explicit non-goals (§18), one commit per sub-step |
| Cross-project/workspace ID references | Med | High | Central scope-validation helper + negative tests for each route family |
| Offline drafts overwrite newer server state | Med | High | Base-revision check + three-way conflict UI; server rejects stale writes |
| Planners regress on real models | Med | Med | Fixture contracts in CI; a documented manual smoke against LM Studio per phase |
| Video workflow blocked by ComfyUI weight-loading faults | Med | Med | Bundled Wan first/last package verified with an env-gated live integration test (`VIDBUILD_COMFYUI_URL`); output kind/mime and FFmpeg thumbnails handled in the worker; the fault is isolated to the ComfyUI/aimdo environment, not the graph |

## 7. Definition of done

Acceptance is spec §19, verbatim. In short: all creative-development, storyboard/continuity,
animatic, prompting/production, phone-workflow and security/reliability statements are
**demonstrably true**, with unit, store, route and end-to-end suites passing from a clean
checkout. The §20 statement is the north star:

> The product is solid when it does not depend on the creator remembering what the
> application failed to model.
